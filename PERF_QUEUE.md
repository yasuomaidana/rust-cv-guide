# Performance priority queue

Operations where the best Rust backend is still slower than OpenCV 5.1.0, biggest gap first. Gaps compare each crate against OpenCV timed with a freshly allocated output, and `opt` is the fat-LTO, native-CPU build. `probe-mismatch` means the backends do different work, so fix the benchmark before trusting the ratio.

**Pick an item:** open its issue, say you are taking it, and set `owner` for it in `catalog/perf_queue.yaml` in your pull request. See `CONTRIBUTING.md` for how to run the benchmarks. The preferred place for a fix is `oxipix`, then a pull request to `imageproc` or `oximedia-cv`.

## Why it is slower, and the fix

- **Template match (TM_SQDIFF)** (researched): OpenCV computes the cross-correlation with a block-wise DFT (templmatch.cpp `convolve_dft`, `getOptimalDFTSize`) and gets the window energies from integral images, so the cost does not grow with the template area. `imageproc::template_matching::match_template` evaluates the sum of squared errors directly for every position: 411 x 261 positions x 1600 template pixels is about 170M multiply-adds, single threaded (its `rayon` feature is off). *Fix:* oxipix wave 1: SSE as `sum(I^2 window) - 2 * corr + sum(T^2)`, with the correlation by FFT (`realfft`) and the window energy from an integral image.
- **Median filter (5x5, r=2)** (researched): median_blur.simd.hpp runs sorting networks for 3x3 and 5x5 windows vectorised across 16 pixels and an O(1) column-histogram method only for large kernels. `imageproc::filter::median_filter` already uses a sliding histogram, but it is scalar, one 256-bin histogram per channel, with a median search per pixel; for a 5x5 window that is far more work than a SIMD network. *Fix:* oxipix wave 1: selection network (min/max passes) over lanes of pixels for radius 1 and 2, histogram fallback for larger radii.
- **Erode (5x5 square, r=2)** (researched): OpenCV erodes with separable running minima on 16 pixels at a time (morph.simd.hpp `MorphRowVec` / `MorphColumnVec`, `ErodeVec8u`). `imageproc::morphology::erode` computes a full distance transform of the mask and thresholds it, which is O(pixels) but with a heavy constant and unrelated to the window size. *Fix:* oxipix wave 1: separable min/max over shifted row slices (vectorises to 16 byte lanes), van Herk / Gil-Werman for large radii.
- **3-level pyrDown** (researched): OpenCV's `pyrDown` does the 1-4-6-4-1 blur in fixed point, horizontal pass into an int row buffer and vertical pass producing only the even rows, SIMD for 1 to 4 channels (pyramids.cpp `PyrDownVecH` / `PyrDownVecV`). The guide's `imageproc::filter::separable_filter_equal` blurs every pixel in f32 with a generic clamped lookup and then throws away three quarters of the result; the oximedia version also builds an intermediate float image. *Fix:* oxipix wave 2: integer separable pass that only computes the kept even rows and columns, per-channel loops over slices.
- **Canny + circle Hough (r=15..40)** (researched): OpenCV's gradient method (hough.cpp, `HoughCircles`) lets each edge pixel vote only along its gradient direction in a 2-D accumulator, then finds the radius from the distances to the centre candidates. `oximedia_cv`'s transform votes for every radius around every edge pixel (a 3-D accumulator, 26 radii here) and builds it from a Canny that is itself 7x slower than OpenCV's. *Fix:* oxipix wave 3: gradient-direction circle Hough on top of the oxipix Sobel/Canny of wave 2.
- **Top-hat morphology (7x7, r=3)** (researched): Same mechanism as erosion, twice (opening = erode then dilate): `imageproc::morphology::grayscale_erode/grayscale_dilate` with a `Mask::square(3)` visit every mask offset for every pixel, O(k^2) with bounds handling, against OpenCV's separable vector min/max. The top-hat then subtracts with a per-pixel `get_pixel` closure. *Fix:* oxipix wave 1: separable grey-scale erode/dilate, opening/closing and a slice-level top-hat.
- **Gaussian blur (sigma=1.1)** (researched): OpenCV's `GaussianBlur` for 8-bit images is a separable fixed-point convolution (smooth.simd.hpp `hlineSmooth` / `vlineSmooth`) with integer kernel weights. `imageproc::filter::gaussian_blur_f32` converts to f32, runs two generic clamped passes and converts back; the work per sample is several times larger. *Fix:* oxipix wave 2: separable integer Gaussian (kernel scaled to 2^k) on u8 slices, one row buffer, no per-pixel bounds checks in the interior.
- **Bilateral filter (d=5, r=2, sc=30)** (researched): OpenCV precomputes the spatial weights once and a 256-entry table for the colour weights (bilateral_filter.dispatch.cpp `space_weight`, `color_weight`), so each tap is two table reads. `imageproc::filter::bilateral_filter` evaluates the Gaussian of the colour distance per tap (a fast `exp` approximation, no table) through the `Pixel` API. *Fix:* oxipix wave 2: bilateral with a spatial table and a 256-entry colour LUT on interleaved u8 rows.
- **Perspective unwarp (4-point quad)** (researched): OpenCV warps with `remapBilinear` on fixed-point coordinates (imgwarp.cpp, `INTER_BITS`), computing the source position incrementally along each row and vectorising the interpolation. `imageproc::geometric_transformations::warp_into` / the oxipix unwarp compute a full projective division and an f32 bilinear sample per output pixel through the `Pixel` API. *Fix:* oxipix wave 3: row-incremental projective coordinates with fixed-point bilinear sampling on u8 rows.
- **Gaussian blur + Canny (50/150)** (researched): OpenCV's Canny (canny.cpp) takes 16-bit Sobel gradients, classifies the direction by comparing `|gy|` with tan(22.5 deg) x `|gx|` (no trigonometry), keeps the candidates in a stack and runs hysteresis over a padded map. `imageproc::edges::canny` computes `atan2` for every pixel in its non-maximum suppression, works on f32 images and runs a generic clamped Sobel, in addition to its own Gaussian blur. *Fix:* oxipix wave 2: i16 separable Sobel, integer direction test, stack-based hysteresis (needs the wave 2 Sobel and Gaussian).
- **Rotate 30 deg + scale 0.6** (researched): Same mechanism as homography, for affine: imgwarp.cpp precomputes the 2x3 matrix in fixed point and steps the source coordinates by constants along each row; the interpolation is SIMD. The Rust crates evaluate the transform and an f32 bilinear sample per pixel through generic accessors. *Fix:* oxipix wave 3: fixed-point incremental bilinear warp (shared with homography).
- **addWeighted (0.5 / 0.5)** (researched): `cv::addWeighted` is one SIMD loop over the raw buffers with the weights as constants (arithm.cpp). The Rust versions walk `Pixel` iterators with bounds checks and per-channel f32 arithmetic, and allocate the output image. *Fix:* oxipix wave 3: slice-level fixed-point `a * w1 + b * w2` over `as_raw()` buffers that the compiler vectorises.
- **Box blur (5x5, r=2)** (researched): OpenCV's `blur` keeps running sums along rows and columns (box_filter.simd.hpp `RowSum` / `ColumnSum`), O(1) per pixel for any window size. The guide builds a box from `separable_filter_equal` with f32 taps, which costs O(window) per pixel. *Fix:* oxipix wave 2: running-sum box blur on u8 slices.
- **FAST-9 corners (t=30, 3x3 non-max suppression, uncapped)** (researched): OpenCV's FAST rejects most pixels with a high-speed test on the four compass pixels (`pixel[0]`, `pixel[8]`, then 4/12, 2/10, ...) and evaluates 16 pixels per step with SIMD (fast.cpp L205-L260). `imageproc::corners::corners_fast9` evaluates the full ring for every pixel and then computes a score, and the non-max suppression and sorting are added on top; `oximedia_cv::FastDetector` has no early-out either (and misses wrapped arcs, see its issue). *Fix:* oxipix wave 3: FAST-9 with compass early-out, 3x3 non-max suppression and top-N selection with `select_nth_unstable`.
- **Sobel X derivative** (researched): OpenCV computes Sobel as separable [1 2 1] and [-1 0 1] passes on 16-bit data with SIMD (deriv.cpp, filter.simd.hpp). `imageproc::gradients::horizontal_sobel` uses a generic 3x3 `filter_clamped` with per-pixel bounds checks and i16 conversion; the snippet then normalises to u8 per pixel. *Fix:* oxipix wave 2: separable i16 Sobel on slices, optional `convertScaleAbs` style output.
- **Contrast + brightness (a=1.3, b=40)** (researched): `Mat::convertTo(dst, -1, alpha, beta)` is one SIMD saturating loop over the buffer. The Rust snippet maps every `Pixel` with an f32 multiply, add and clamp, and allocates the output. *Fix:* oxipix wave 3: slice-level fixed-point scale and shift with saturation.
- **FAST + BRIEF matching (t=20, 250 kp, up to 32 bits)** (researched): The row is dominated by detection (two FAST runs, see `feature_detection_fast`), followed by the descriptor and Hamming matching of 250 x 250 pairs. OpenCV's BRIEF samples with integral images and compares byte-packed bits with SIMD popcount; the Rust matcher is a scalar double loop over `u128` pairs and `Vec<bool>`-style intermediate results in the shared sampler. *Fix:* oxipix wave 3: FAST (above), integral-image BRIEF writing straight into `[u128; 2]`, matcher over packed words with `count_ones`.
- **2D convolution (5x5 box kernel)** (researched): `cv::filter2D` with a 5x5 kernel runs a SIMD correlation (filter.simd.hpp) on rows that are padded once, so the inner loop has no bounds checks. `imageproc::filter::filter3x3`/the guide's generic kernel path clamps coordinates for every tap and converts through f32 per channel. *Fix:* oxipix wave 2: padded-row f32 correlation with a const-generic kernel size, plus a separable fast path when the kernel is rank 1.
- **Distance transform (L2)** (researched): OpenCV's `distanceTransform(DIST_L2, 3)` is a two-pass 3x3 chamfer approximation (distransform.cpp, forward and backward mask), i.e. it does less work than an exact Euclidean transform. `imageproc::distance_transform` is exact (Felzenszwalb and Huttenlocher style) and uses wider intermediate types, so part of the gap is different work, not slowness. *Fix:* oxipix wave 3: 3x3 chamfer variant with an exact-Euclidean option, and mark the row's semantic difference.
- **Canny + standard Hough lines** (researched): Almost all of the time is the Canny before the transform (about 18 of 20 ms); OpenCV's `HoughLinesStandard` (hough.cpp) uses precomputed sine and cosine tables and integer rho. The transform itself is 1.0 to 1.5x of OpenCV's. *Fix:* Follows the wave 2 Canny; no separate kernel needed.
- **PSNR** (researched): OpenCV computes PSNR with `absdiff`, a float conversion, a multiply and `sum`, each a SIMD pass. The Rust version converts through `Pixel` iterators and accumulates in f64 with bounds checks. *Fix:* oxipix wave 3: single fused pass over two slices accumulating integer squared differences.
- **Gaussian blur + Laplacian edge** (researched): OpenCV's 3x3 Laplacian on 8-bit input is a specialised SIMD kernel producing 16-bit output. `imageproc::filter::laplacian_filter` runs the generic clamped 3x3 path, and the snippet adds a Gaussian blur and a per-pixel normalisation pass. *Fix:* oxipix wave 2: i16 3x3 Laplacian on padded rows (shares the Sobel code) with slice-level normalisation.
- **SSIM (11x11 Gaussian)** (researched): OpenCV's SSIM sample is five Gaussian blurs of f32 images plus element-wise operations, all vectorised. The Rust version uses generic f32 blurs and per-pixel loops; it is already within 2x. *Fix:* oxipix wave 3: reuse the wave 2 separable Gaussian in f32 and fuse the element-wise maths.
- **Find contours + approxPolyDP** (researched): OpenCV's `findContours` (contours_new.cpp) is a tight border-following loop on a padded byte image; the oxipix tracer is within 1.6x already, the gap is the per-step bounds checks and a `Vec<Point>` per contour. *Fix:* oxipix wave 3: padded-image tracing without bounds checks.
- **Otsu binary threshold** (researched): OpenCV's Otsu threshold builds the histogram and applies a SIMD compare (thresh.cpp). The Rust versions build the histogram through `Pixel` iterators and write the output with `put_pixel`. *Fix:* oxipix wave 3: histogram and threshold on raw slices.
- **HSV red range mask** (researched): OpenCV converts to HSV with a SIMD `cvtColor` (color_hsv.simd.hpp) and `inRange` with SIMD compares. The Rust versions convert per pixel with f32 maths and compare through `Pixel` iterators. *Fix:* oxipix wave 3: integer HSV conversion and range test fused in one slice pass.
- **Histogram equalisation** (researched): Both stages are cheap in OpenCV (histogram, 256-entry LUT, `LUT` SIMD apply); the Rust versions are close (1.2x). The remaining gap is the per-pixel `get_pixel` / `put_pixel` access. *Fix:* oxipix wave 3: slice-level histogram and LUT application.

## Known differences

Rows whose backends cannot run the same work, with the reason.

- **FAST-9 corners (t=30, 3x3 non-max suppression, uncapped)**: oximedia-cv FastDetector counts the 9 contiguous ring pixels linearly over indices 0 to 15 and never detects an arc that wraps around the ring, so it returns 1424 corners where FAST-9 (OpenCV, imageproc) returns 2091 and 2204. The oximedia column is therefore not a full FAST-9; reported upstream as https://github.com/cool-japan/oximedia/issues/32.
